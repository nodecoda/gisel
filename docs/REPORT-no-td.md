# 移除 `.td` 渲染器：把 TableGen 从代码里断干净

状态：完成。基线 `22f367e`。本报告是当时的快照：那时 8 份冻结产物，现在
12 份（新增 RISC-V 自基线）。本报告记录“第 5 个渲染器”被切断后，哪些
TableGen 代码被删除、哪些冻结文本被迫保留，以及为什么“彻底到零 TableGen
字面量”会与既有产物/语料契约冲突。

## 1 删掉了什么

| 删除项 | 原位置 | 原因 |
|---|---|---|
| `--emit=td`、`--td` 别名、默认 `td` | `gisel/cli.py` | `.td` 不再是产品后端 |
| `gisel/td.py` | 整个文件 | `.td` writer + `.td` reader + bootstrap |
| `gisel bootstrap` | `cli.py` / `td.py` | 反向导入器只服务 `.td`，一并移除 |
| `dsl.TdEmitter`、`_llt_leaf`、`render_*` | `gisel/dsl.py` | `.td` 专用渲染器 |
| `_parse_td_defs`、`build_arity_manifest` | `gisel/dsl.py` | TableGen 语法解析器 |
| `tools/gen-opcode-table.py` | `tools/` | 只用于从 `GenericOpcodes.td` 重建 arity |
| `tests/golden/*.td` | `tests/golden/` | 没有消费者 |
| `Include` AST 节点 | `gisel/ast.py` | `.td` 的 include 透传；现在解析时忽略 |
| `PredicateDecl.source`、`SelectType.arms/otherwise`、`TypeSet.members/source_ref`、`TypeList.members` | `gisel/ast.py` | 仅 `.td`/record 适配器使用；`TypeList` 名称改由 `value` + `NameTable` 计算 |
| `NameTable.rule_view/node_view/select_view/set_name_td` | `gisel/ast.py` | `.td`/旧 record view |
| `to_record_model` | `gisel/ast.py` | 迁移期的 record 模型 oracle |

删除后，生产路径只剩下四个后端：

```
inc    AST -> C++ legalizer chain .inc
check  AST -> counter JSON
table  AST -> C++ type-class/table .inc
core   AST -> schema-0.4 JSON -> eval
```

`gisel gen` 的默认 `--emit` 改为 `inc`；当时 `--emit` 的合法值是这四个。

> 2026-11-09 更新：`table` 也已删除（`gisel/backend/table.py`、`--emit=table`、
> `tests/artifacts/*.table.inc`、`tests/artifacts/SHA256` 里对应的三行）。
> 现在只剩 `inc` / `check` / `core`，产品就是 `inc`。

## 2 为什么还看得见 `.td` / TableGen 字样

有三类残留，性质不同：

1. **冻结产物里的 banner**  
   `tests/artifacts/x86.inc` 等文件是逐字节 oracle，其中包含
   `TableGen'erated file`、`Generated by llvm-tblgen` 等注释。`llvm_inc.py`
   和 `table.py` 必须继续输出这些字符串，否则校验立即失败。这里的
   `llvm-tblgen` 带的是本项目分支新增的 `-gen-legalizer` 后端，不是上游
   main 的能力（`docs/CORPORA.md`）。这是产物契约，不是代码依赖。
2. **冻结语料里的 `include` 行**  
   `tests/corpus/*.gisel` 按约束不动，仍有
   `include "llvm/Target/LegalizerInfo.td"`。`ast.parse_program` 现在接受并
   忽略 include 行；它不再进入 AST，也没有消费者。导入器
   `tools/import-cxx.py` 仍会写出这两行，因为 `tests/test_import_cxx.py`
   要求重新导入的语料与仓库内语料逐字节一致；导入器是开发工具。
3. **冻结数据/开发脚本**  
   `gisel/data/generic_opcodes.json` 的数值是冻结的 opcode arity 表；`source`
   字段已改为不含 `.td` 路径的描述。`tools/refresh-oracle.sh` 仍是开发期
   oracle 刷新脚本，会调用 `llvm-tblgen` 生成 `.inc`/JSON；`gisel` 本身和 CI
   不调用它。`gisel/vocab.py` 的 50/64/64 是 `--emit=check` 的冻结计数器。

因此当前状态是：

> **运行代码里没有 TableGen 解析/渲染；仍存在冻结文本和开发期 oracle。**

## 3 为什么不能字面“零 TableGen”

要同时满足：

- `tests/corpus/*.gisel` 一个字节不改；
- 8 份 `tests/artifacts/*` 逐字节不变；
- 34,776 点差分不变；

就不能删除语料里的 include 行，也不能删除 `.inc` 产物里的 TableGen banner。
唯一能做到“字面零 TableGen”的办法是修改语料并重生成产物，这会直接解除原先的
三条硬约束。本提交选择保留冻结文本，只切断**代码/模型/后端**层的依赖。

如果未来允许改语料与产物，最小步骤是：

1. 从 5 份语料删掉两行 include（或改成普通注释）；
2. 重生成 8 份 artifacts，去掉 banner（同时接受 SHA256 全变）；
3. 删除 `tools/refresh-oracle.sh` 与 `vocab.py` 的历史注释；
4. 把 `docs/REPORT-ast.md` 里“第 5 个渲染器”的表述改成历史章节。

(cd tests/artifacts && sha256sum -c SHA256)    # 8/8

## 5 已知边界

- `--emit=td`、`--td`、`gisel bootstrap` 已移除；旧命令会得到 argparse 的
  `invalid choice`，这是有意的 CLI 变更。
- `include` 行仍被接受但忽略；不报错，以免冻结语料无法解析。
- CI 的 `llvm-tblgen` shim 只覆盖四个后端；`tools/refresh-oracle.sh` 不在 CI。
- `TableGen` 字样仍出现在冻结 `.inc` banner、历史 docs 和
  `docs/REPORT-riscv.md` / `REPORT-wasm.md` 的历史段落里。
- 原 Phase 3 的 `bootstrap --td … | cmp corpus` 门禁随读取器一起退休；
  替代证据是 5 份语料逐字节未改、8/8 artifacts、68 tests。
- `--emit` 默认为 `inc`；旧脚本若依赖默认 `td` 需要显式改参数。
